## 1. 解く痛み（見失わないため再掲）

柴山さんがミツメルに書いた日次記録を、**普段使うGoogle Driveの`ミツメル日次記録`フォルダで見返せる**ようにする。今は書きっぱなしでDriveに残らない。

## 2. なぜサービスアカウントではダメで、この形になるか

- サービスアカウント（JWT署名）は個人Driveに新規ファイルを作れない（403 storageQuota・実測済み）。
- → **柴山さん本人のアカウントのOAuth2**で書く。本人の容量に書くので制約に当たらない。
- → 本人アカウントで無人のWorkerが書き続けるには**refresh_token**が要る。

### ⚠️ 技術判断①：ブラウザのGISはデフォルトでrefresh_tokenを返さない

Google Identity Services（GIS）の**トークンモデル**（`initTokenClient`）は短命アクセストークン（約1時間）しか返さない。**refresh_tokenを得るには「認可コードモデル（`initCodeClient`）→サーバーが認可コードをrefresh_tokenに交換」の流れが必須**。

したがって構成は：
- **フロント**：認可コードを取得（同意は初回1度）＋Pickerでフォルダ選択
- **Worker**：認可コード→refresh_token交換（`client_secret`はWorker Secret）／以降refresh_token→access_token交換して書き込み

これは「認証関数だけ改修」では収まらず、**フロント＋Worker両方**になる（発注時に工数見積りとして共有済み）。

### ⚠️ 技術判断②：Web applicationクライアントは client_secret 必須（refresh交換のPOSTは4パラメータ）

リサーチ照会で確定（公式原文：`"a JavaScript application does not require a secret, but a web server application does"`）。今回は「Web application」クライアント＝confidential clientなので、**refresh_token交換のPOSTボディは`client_id & client_secret & refresh_token & grant_type=refresh_token`の4つ**。ネット上に多いnative-app（public client）の3パラメータ例（client_secret無し）をコピペすると`invalid_client`で詰まる。**client_secretはWorker Secret（`GOOGLE_OAUTH_CLIENT_SECRET`）に置き、フロント・ソースに出さない**（confidential clientの正しい扱い）。認可コード交換のPOSTも同様にclient_secretを含める。
- ★実地検証で、secret無しだと`invalid_client`が返ることを1回確認すれば、この必須性も同時に実物確定できる（リサーチの★未確認も同時に閉じる）。

## 3. データフロー（初回セットアップ／毎日の書き出し）

### 初回セットアップ（柴山さんが1度だけ）
```
[mitsumeru_private.html]
  柴山さんが「Google Driveに書き出す設定」ボタンを押す
  → GIS code client（drive.file, access_type=offline, prompt=consent）で同意 → 認可コード取得
  → Google Picker（Picker API）で ミツメル日次記録 フォルダを選択 → folderId取得
  → POST /vault-oauth-setup { code, folderId } を Worker へ
[worker.js /vault-oauth-setup]
  → token endpoint へ code 交換（grant_type=authorization_code, client_id, client_secret, redirect_uri）
  → refresh_token と folderId を KV に保存（例：vault_oauth_refresh / vault_oauth_folder）
  → フロントへ ok
```

### 毎日の書き出し（無人・夜の締め）
```
[mitsumeru_private.html closeDayHPMP()]
  → 既存 syncToVault() が POST /sync-vault を叩く（配線は既に存在）
[worker.js /sync-vault]（改修）
  → KV から refresh_token + folderId を読む
  → token endpoint へ refresh_token 交換（grant_type=refresh_token）→ access_token
  → drive.file で folderId 内に {date}.md を検索 → あれば PATCH／なければ multipart POST
  （※この検索・作成ロジックは既存 handleSyncVault のものを流用。認証取得部分だけ差し替え）
```

## 4. 認証パスの分岐（⚠️カレンダーJWTは温存）

現状 `getGoogleAccessToken(env, scope)` は**サービスアカウントJWT一本**。これを用途で分ける：

| 用途 | 認証 | 変更 |
|---|---|---|
| **カレンダー**（/sync-calendar） | サービスアカウントJWT（現状） | **触らない** |
| **Vault**（/sync-vault） | 柴山さんOAuth2 refresh_token | **ここだけ差し替え** |

- 新関数（案）：`getVaultAccessToken(env)` … KVのrefresh_token→access_token交換（HTTPS POSTのみ）
- 既存 `getGoogleAccessToken` はカレンダー専用として残す（呼び出しは1箇所＝263行のカレンダーのみになる）
- **回帰リスクの封じ込め**：カレンダー経路の関数・呼び出しに一切手を入れないことで、カレンダー連携への回帰を構造的にゼロにする

## 5. 必要なSecret / KVキー（追加分）

- Secret（追加）：`GOOGLE_OAUTH_CLIENT_ID`（公開値だがSecret管理で可）・`GOOGLE_OAUTH_CLIENT_SECRET`（秘密）
- KV（追加）：`vault_oauth_refresh`（refresh_token）・`vault_oauth_folder`（folderId）
- 既存 `GOOGLE_VAULT_FOLDER_ID`（Secret）は、Picker選択に置き換わるため**将来的に不要**になる可能性。ただし当面は残す（Pickerを使わずSecret固定でも動くフォールバックとして）。判断は実装時。
- 既存 `GOOGLE_SERVICE_ACCOUNT_KEY`・`GOOGLE_CALENDAR_ID`：カレンダー用にそのまま。
